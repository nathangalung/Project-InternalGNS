# InternalGNS — Consolidated Engineering Audit

Synthesis of 7 domain audits (backend architecture, data layer, auth/security, frontend architecture, frontend performance, infra/ops, money & domain invariants). Findings merged across domains; every row keeps `file:line`.

---

## 1. Executive verdict

The skeleton is better than the defect list suggests, and the defects are not where a generic review would look. Middleware order is deliberate, `ORDER BY` is whitelist-mapped everywhere (no injection surface found by any of the seven passes), refresh-token rotation with reuse detection is textbook, money never touches a float in the persisted path, and the state machines take `FOR UPDATE` before they read status. What is broken is the **edges**: every place a second implementation of an authoritative rule was allowed to exist, and every place a policy has two owners. Pagination is owned by both the HTTP layer and the repo, so all four XLSX exports — including the DJP e-faktur bulk filing — silently stop at 200 rows. The PPN formula exists three times (SQL, Go PDF helper, TS preview) with three rounding models. The invoice PDF totals block still renders the quotation's layout, so it prints an arithmetic identity that has been false since migration 00021.

The single structural root cause on the backend is one type choice: `Deps.Pool` is `db.Executor`, which has no `Begin`, so no feature slice can open a transaction. `shared/db/WithTx` exists and is called only by its own test (verified). That is why business logic migrated into plpgsql, which is why domain errors arrive as untyped `P0001`, which is why Go repos classify them with `strings.Contains`, and why a 500-row import creates catalog items non-atomically. On the frontend the equivalent is `_authed.tsx` rendering a bare `<Outlet/>`, which pushed the app shell into 20 leaf components and spawned a hand-written string-union router shadowing the typed route tree.

Two claims in `CLAUDE.md` are not true today and should be corrected rather than defended: feature packages are not self-contained (`invoices` imports four sibling slices), and RBAC is not enforced "at the middleware and the handler" — every non-dashboard handler has zero role checks and relies solely on the mount, while `/dashboard` is the one subtree with no mount gate at all. Health is "sound foundation, leaking at every seam where a rule was duplicated" — this is a consolidation job, not a rewrite.

## 2. Strengths to preserve — a refactor must not break these

- **`httperr.FromDBErr` never leaks driver text.** `shared/httperr/httperr.go:59-77` maps SQLSTATE→HTTP with a curated message; `RenderDBErr:80-86` logs the real error only on 5xx. Do not "improve" this by surfacing `err.Error()`.
- **`ORDER BY` is never built from user input.** Every repo maps `sortBy` through a closed switch to a fixed column expression (`clients/repo.go:62-71`, `items/repo.go:52-58`, `purchaseorders/repo.go:74-84`). The shared builder in §6 must inherit the whitelist, never accept a column name.
- **Refresh-token rotation.** 32 bytes CSPRNG, SHA-256 at rest, atomic redeem-and-revoke in one statement (`db/queries/auth.sql:13-18`), reuse detection with a documented 10s grace window (`auth/service.go:155-176`). Never replace the atomic `UPDATE … RETURNING` with SELECT-then-UPDATE.
- **JWT verification hardening.** `WithValidMethods(["HS256"]) + WithIssuer + WithExpirationRequired` (`auth/service.go:232-236`) closes alg-confusion and never-expiring tokens in one place.
- **Lock-first status machines.** `fn_change_quotation_status` (00040:17-20), `fn_change_po_status` (00035:39-41), `fn_change_invoice_status` (00025:22-25), `fn_update_po_items` (00027:22-25) all `SELECT … FOR UPDATE` before reading status. 00040 deliberately moved the unpriced-product guard *into* the locked region. **Do not refactor these into Go-side pre-checks** — that reintroduces the TOCTOU 00040 closed.
- **Optimistic locking done right on the newest paths.** `fn_update_quotation_versioned` / `fn_update_po_items_versioned` (00029) raise dedicated SQLSTATEs P0010/P0011 mapped by code, not message (`purchaseorders/repo.go:244-252`). This is the pattern everything else should converge on.
- **Money is exact NUMERIC end-to-end and invoice lines are immutable.** Generated columns evaluate exactly (00010:94-99); grep confirms no production path INSERT/UPDATE/DELETEs `invoice_items`. That immutability is what makes 00039's "header = SUM(line)" model hold at runtime. Any future "edit invoice line" feature must recompute the three header columns in the same transaction.
- **Migrations run under a Postgres advisory lock** (`shared/db/migrate.go:27-36`) — the single most important precondition for ever running >1 replica, already correct.
- **`queries.Load()` fails at boot, not at runtime** (`db/queries/queries.go:28-52`): parses all embedded SQL, rejects duplicate block names, validates against `RequiredKeys`. `Store.Get` panicking is the *right* call given that validation — fix the validation gap (H18), don't soften the panic.
- **MinIO is not publicly routed.** No Traefik router, `internal: true` network, all bytes proxied through the authenticated API (`infra/dokploy/docker-compose.yml:46-48`, `storage/minio.go:100-108`). Reintroducing real presigned URLs would put object storage on the public internet.
- **Storage download is defensively correct**: Content-Type derived from the allow-listed extension, forced `attachment` disposition (`storage/handler.go:96-105`), plus CSP/X-Frame-Options/nosniff on every response.
- **`trustedProxyIP` takes the *last* XFF hop** (`app/middleware.go:16-30`) and documents why. Correct behind a single reverse proxy; trivially broken by "fixing" it to take the first hop.
- **Frontend data layer.** Single-flight refresh dedupe with recursion guard and body drain (`lib/api-client.ts:55-112`); `throwOnError: (e) => !(e instanceof ApiError) || e.status >= 500` (`lib/query-client.ts:14`) deliberately splits 5xx→boundary from 4xx→inline; `queryKeys` is prefix-consistent so `invalidateQueries({queryKey: X.all})` cascades correctly.
- **The quotation wizard renders one step at a time** (`QuotationEdit.tsx:369-444`) and slices product lists to 5 rows. There is no re-render storm. Do **not** "optimize" by mounting all steps and hiding with CSS — that is what would create one.
- **Every list screen is server-paginated** (10-25 rows/render). Virtualization would add a dependency and solve nothing.
- **`exceljs` is behind a dynamic import** (`uploadParser.ts:112`) and `TrendChart.tsx` is hand-rolled SVG with no charting library. Both correct; leave them.
- **The xelatex semaphore primitive** (`pdfgen/pdfgen.go:20-30`) — package-global, sized from CPU, acquired with `select` on `ctx.Done()`. The bug is in the timeouts *around* it (#21), not this design.
- **Migration 00039 is the standard for money migrations**: it explains why header PPN stopped being GENERATED, states which rows the backfill touches, and ships a read-only per-year diff query to hand to whoever signs off with DJP.

## 3. Critical and High findings

**Severity bar, applied uniformly:**
**Critical** = a wrong number on a document already sent to a client or filed with DJP.
**High** = confirmed wrong data or silent data loss visible to users, a security hole with a realized path, or a structural blocker to other fixes.

**Rank order:** tax/legal correctness → silent data loss → security → structural coupling → ops.

**Conflict rule:** where two domain audits graded the same code differently, this report takes the **higher severity and the more conservative `behavior-change`** flag. Both auditors read the same lines; the stricter read is the safe default. (Applied to #18 RequiredKeys, promoted medium→high; and to the error-classification finding in §4, behavior-change→Y.)

**Security (medium/low)**
- **`/dashboard` is the only subtree with no mount-level `requireRole`** (`router.go:110`). - **Login discloses whether an email is registered** and returns *before* bcrypt for unknown accounts — three distinguishable responses plus a ~60-100ms timing oracle that survives message unification. An attacker enumerates staff at 5 req/min then aims the per-account lockout at them: 5 wrong passwords = 15 min lockout, repeatable indefinitely, no alerting. Fix: one message and one status for all credential failures, and always compare against a fixed dummy hash. (`auth/service.go:74-97`)
- **`UNIQUE(email)` is case-sensitive; every auth lookup is `LOWER(email)`.** `users.create` performs no LOWER check, so `Admin@gns.com` can coexist with `admin@gns.com`. `pgx.CollectOneRow` returns the **first** row without erroring on extras and the query has no ORDER BY — so which account authenticates is up to the planner, and a failed login increments both lockout counters. Fix: `CREATE UNIQUE INDEX users_email_lower_idx ON users (LOWER(email))` (the codebase already does exactly this at `00001:356` for company_contacts) + normalize on write. **`ORDER BY id LIMIT 1` is not the fix.**
- **Storage proxy authorizes the bucket but never the object key.** `safeKey` blocks traversal and the extension allow-list holds, but nothing ties the key to the record being acted on and nothing prevents overwriting an existing object. Fix: sign the `{bucket,key,method,exp}` tuple with the JWT secret at presign time and require it on the proxy call — that restores the property presigning was meant to provide. - **`trustedProxyIP` rewrites RemoteAddr from an unauthenticated header** with no check that the request came from the proxy. Correct behind Traefik; the trust assumption is a comment, not code. If the API is ever reached without the proxy, the login rate limit disappears entirely and access logs become attacker-authored. Fix: trust the last hop only when the direct peer is in a configured CIDR list (default empty = trust nothing); log both peer and derived IP.
- **CORS wildcard and superadmin-password checks are enforced only when `ENV==production`**, and Env defaults to `development` with `CORS_ALLOWED_ORIGINS` defaulting to `*`. Do not add Redis now — record the per-instance constraint in the README as the honest cost of single-node (Q7).

- **Dependency wiring happens in the leaves.** `NewHandler(repo)` takes only the repo, so each slice pokes `h.storage = d.Storage` from its own `routes.go` — a new slice that forgets the line **compiles fine** and returns `503 storage not configured` at runtime. Separately, slices construct each other's repos: `invoices/routes.go` builds `clients`, `quotations` and `purchaseorders` repos; `purchaseorders` builds `clients`+`quotations`; `quotations` builds `clients`+`units`. The import graph is a one-way DAG **by luck** — the first time `quotations` needs anything from `invoices` the compiler forces an unplanned redesign under deadline. Fix: `NewHandler(repo, storage)` so a missing dep is a compile error; construct shared repos once in `app.NewRouter`, or define narrow consumer-side interfaces (`invoices.ClientLookup`).
- **Pure ranking logic lives in the HTTP layer.** `tierWeight`/`classifyItem`/`mergeAdvanced`/`contains`/`autoCreateKey` are 130 dependency-free lines wedged between HTTP handlers — and the package already contains `items/merge_test.go`, **a test file named after a `merge.go` that does not exist**. The seam is drawn; the move was never made. Same mildly for `parseListFilter`/`parseDateParam`/XLSX row-shaping in the PO and invoice handlers, where `quotations/export.go` already establishes the pattern. Pure file moves, no signature changes.
- **`parseDateParam` is byte-for-byte identical in two handlers**; `const exportMaxRows = 100000` is declared **three** times (verified: `purchaseorders/handler.go:75`, `quotations/handler.go:68`, `invoices/handler.go:84`). This is why #1 had to be fixed in four places, and why the sentinel drifted from the repos' 200 without anyone comparing them. Fix: `parseDateParam` → `shared/httpx`; the sentinel → one constant beside `paginate.MaxLimit`.
- **`shared/money` and `shared/tz` are almost entirely dead**, and the dormant path hides a trap: `DPPRatio = decimal("11").Div("12")` evaluates at shopspring's default 16-place `DivisionPrecision`, so `DPPNilaiLain` is **truncated 11/12, not exact**. Not a live bug — only three string constants have a caller — but it is a correct-looking sanctioned-helper API that will introduce sub-cent drift the first time someone reaches for it. And `tz`'s zero callers are *why* `CURRENT_DATE` leaked into `fn_create_invoice` unchallenged (#3). Fix: delete, or make them real by routing #3's pool timezone and `quotations/export.go` through them so a regression would be caught.
- **`CREATE INDEX CONCURRENTLY` + `IF NOT EXISTS` under auto-migrate-on-boot can leave a permanently invalid index.** A boot timeout partway leaves an INVALID index and the migration unrecorded; the next boot's `IF NOT EXISTS` sees it **by name** and skips. The index then exists, is never used by the planner, and is maintained on every write forever, with no error anywhere — including the quotation search indexes the list filter genuinely depends on. Nothing checks `pg_index.indisvalid`. Fix: boot/CI check failing on `WHERE NOT indisvalid`; use drop-then-create in new CONCURRENTLY migrations so a retry repairs rather than skips. (`00034:1-8`, `00038:1-24`)
- **Down migrations restore stale function bodies.** Holds by hand-verification only (00035's Down is byte-identical to 00030's Up) and degrades as the chain lengthens. **00039's Down is actively destructive**: it drops `dpp_nilai_lain`/`ppn_amount`/`total` and re-adds them as GENERATED, discarding the per-line-summed values the Up was written to preserve — i.e. the numbers filed with DJP. Fix: falls out of #19; for 00039 specifically, replace the Down with `RAISE EXCEPTION 'irreversible'`.
- **Migrations, seeding and bcrypt all run before the HTTP listener exists** (`app/server.go:17-40`), so `/healthz` and `/readyz` answer nothing during boot, against a 30s `start_period`. A slow migration pushes boot past it and Docker begins marking a legitimately-working container unhealthy — which on some orchestrators restarts it and re-runs the migration from scratch. This is the concrete blocker to >1 replica, more limiting than the pool size. Fix: two-phase boot — listen immediately with `/healthz` up and `/readyz` not-ready, run migrations in the background, flip readiness. Minimum: wrap the migration call in its own generous timeout so a stuck advisory lock fails loudly rather than hanging forever.
- **Container healthcheck probes readiness, not liveness.** `--healthcheck` hits `/readyz`, which pings the DB, so a transient Postgres blip fails three checks and Docker restarts a process that was fine — turning a brief hiccup into a longer outage. `/healthz` exists at `router.go:51-54` and nothing uses it. The frontend separately sets `healthcheck: disable: true`, discarding the working check its Dockerfile defines, so a wedged nginx is invisible to the platform.
- **Docker logs are unbounded** — no `logging:` block in either compose file, so json-file grows monotonically under `restart: unless-stopped`. Because Postgres and MinIO write to volumes on the same filesystem, a full disk stops DB and object-store writes, and the failure presents as a confusing cascade rather than "disk full". Fix: `max-size: 10m, max-file: 3` via a YAML anchor — **check whether Dokploy already sets a daemon-level default first**; if so this is a README note, not a change.
- **MinIO has no documented backup path while Postgres does.** The Operations table has a Postgres backup row and, for MinIO, only console access. The volume holds every PO scan, logo, item image and invoice attachment on a single node with no replication, no bucket versioning (`storage.New` uses default options) and no lifecycle policy. Volume loss makes every `object_key` a dangling pointer. **The asymmetry is the tell** — someone thought about Postgres durability and the object store never came up. Note the ordering hazard: running the orphan-blobs sweeper against a restored-from-older-backup database **deletes newer objects**; document that constraint next to the sweeper.
- **Handler-level error logs carry no request id.** The access-log middleware emits `request_id`, but the default `slog.NewJSONHandler` at `main.go:22` **ignores context entirely**, so every `slog.WarnContext(r.Context(), …)` call site adds nothing. An error line and its access-log line cannot be joined; correlation is by timestamp across interleaved concurrent requests. Log level is also hardcoded to Info with no env override, so raising verbosity needs a redeploy. Fix: ~20-line `slog.Handler` wrapper pulling `middleware.GetReqID(ctx)` into every record — fixes every existing call site at once — plus `LOG_LEVEL` in Config. For the xelatex bottleneck, log the queue wait when a render waits >1s; that is the leading indicator whose absence is why #22's OOM scenario would arrive without warning. **Do not add Prometheus/OTel for a single-node internal tool** unless that log proves insufficient.
- **Expired refresh tokens are never purged.** `auth.refresh_purge_expired` is defined **and listed in `RequiredKeys`** — so startup validation forces it to keep existing and it *looks* wired — but grep finds no caller. Impact is contained (`token_hash` is UNIQUE, so lookups stay index scans; a few thousand rows/year), and the real cost is the misleading appearance of a retention policy, plus indefinitely retained revoked hashes alongside `user_id`. Fix: a ticker goroutine in `NewServer`, or delete the query and its entry. **Do not add an external scheduler.** *(Flagged independently by two audits.)*
- **Pool size hardcoded at 20 with no env override** (`shared/db/pool.go:15-16`), overriding whatever the DSN says, against `max_connections=200`. Comfortable today; the same function is used by the orphan-blobs sweeper, which needs one connection and takes twenty. Add `DATABASE_MAX_CONNS` with default 20 when next touching the file — not independently urgent.
- **Dead client-side filter branch** in the quotation wizard: the fallback filter only runs when `remoteClients.length === 0`, in which case `sortedClients` is also empty — so it can only ever return `[]`. Unreachable code that reads as working fallback logic. (`QuotationEdit.tsx:129-138`)
- **Undocumented convention split:** `useCreateVendor`/`useCreateItem`/`useAddVendorToItem` omit `onError` toasts while their `useUpdate*` siblings have them. Verified intentional — all three callers render inline `setSubmitError` — but write it down or the next hook picks the wrong side.

## 5. Clean architecture: how it should be organized, and where the code violates it

### Backend — intended layering

```
cmd/api            process lifecycle only
  └── app          COMPOSITION ROOT: router, middleware, DI, config
        └── <feature>   handler (HTTP) → repo (SQL) → dto ; domain logic in its own file
              └── shared   db · httperr · httpx · paginate · listq · assetproxy · storage · money · tz
                    └── db/queries (named SQL)  +  db/functions (canonical plpgsql)
```

Three rules follow: **composition belongs to `app`, not to leaves**; **a handler contains no logic that does not touch `http`**; **each policy has exactly one owner**.

**Violations, in dependency order (fix upward):**

1. **The DI seam is too narrow, so the layering inverted.** `Deps.Pool` is `db.Executor` (no `Begin`), so transactional logic could not live in Go and migrated into plpgsql (#17). That produced untyped `P0001`, which forced Go repos to classify domain errors by substring-matching English exception text (§4), and left the 500-row import non-atomic. **This is the spine — every other backend violation is downstream of it.** Widen the seam first; then per-function "SQL vs Go" becomes a real choice (Q4) instead of a forced one.
2. **Composition happens in the leaves.** `routes.go` files poke unexported fields (`h.storage = d.Storage`) and construct sibling repos — `invoices` imports four sibling slices. `CLAUDE.md`'s "self-contained package per resource" is false; correct the doc and move construction into `app.NewRouter`.
3. **Policy has two owners in three places:** pagination (HTTP `paginate` + repo clamp → **#1, the critical bug**); "effectively overdue" (SQL summary + Go filter builder + three TS copies → **#7**); the PPN formula (SQL + Go PDF + TS preview, three rounding models). Each needs a single owner, and in all three cases the owner should be the layer nearest the data.
4. **SQL fragments are written in Go.** Seven repos assemble WHERE/ORDER BY as Go string literals — the one place the "SQL lives in `.sql` files" rule breaks — and the `total_purchase` correlated subquery exists as Go text twice and as SQL once (#25).
5. **Pure logic sits in the HTTP layer.** `items/handler.go` is 622 lines mostly because a dependency-free merge/ranking algorithm lives between handlers, plus ~100 lines of the copy-pasted presign triplet (#24).
6. **RBAC's structural default is opt-in on exactly the subtree handling revenue** (`/dashboard`, §4). Default-deny should be the mount's job everywhere.
7. **`RequiredKeys` is a hand-kept ledger** standing in for a derived invariant (#18).

## 7. Open questions for the owner

Two of the three examples in the brief already have one-sided evidence. Stating a verdict is more useful than manufacturing a debate.

**Q1 — Hand-maintained types vs codegen. Verdict: keep hand-maintained; delete the codegen scaffolding. Not a real question.**
Evidence is one-sided: `types/openapi.gen.ts` has **zero importers (verified)**; `openapi.yaml` documents **2 of ~90** registered routes; the Go handlers carry no spec annotations, so the YAML is itself hand-written. Adopting codegen means hand-writing 88 more endpoints of YAML — strictly more maintenance than the 576-line `types/api.ts`, and the YAML would drift from the DTOs by the same mechanism. Delete the file, both scripts, the dep and `ci.yml:90-91`, and close the real drift risk with the seven missing fields plus a Go DTO-marshal golden test. **The narrower question that remains for you:** later, do you want TS generated from the Go json tags (which *are* the source of truth), or is the golden test enough? Recommendation: the golden test.

**Q2 — Should the invoice show a discount at all?** This is the only genuine ambiguity in #2 and it blocks the fix. Two options: (a) drop the Diskon row — the discount is already inside `unit_price` since mig 00021, the invoice becomes internally consistent, and clients no longer see the discount broken out; or (b) print gross `unit_price` per line and store the discount on the invoice — that is a **schema change plus a template change**, not a template tweak. Pick before Phase 1.

**Q3 — Is dashboard revenue and profit meant to be VAT-inclusive?** `total_revenue = SUM(invoices.total)` where `total = dpp + sum_ppn` (00039:34), and `profit = revenue − expenses` where expenses is `SUM(qty × cost_price)`. **Blocked on a fact not establishable from the repo: is `cost_price` recorded ex-VAT?** If yes and the intent was net-of-VAT, the profit figure finance reads daily is overstated by roughly 11% of DPP. Gross-of-VAT reporting is also common practice in Indonesian SMEs, in which case nothing is wrong. Either way the basis is undocumented and `total_ppn` sitting alongside invites the question — comment it in `dashboard.sql` once you answer.

**Q4 — SQL functions vs Go logic, per function.** Today this is not a choice — `Deps.Pool` has no `Begin`, so plpgsql was the only place multi-statement work could live. **Ask this question only after #17 lands**, and answer it per function, with one hard constraint: **the lock-first `FOR UPDATE` status machines must not become Go pre-checks.** Mig 00040 deliberately moved a guard *into* the locked region to close a TOCTOU; reversing that is a regression, not a refactor. Recommendation: keep state transitions and invariants in SQL under the row lock; move everything else (item matching, ranking, export shaping, batch imports) into Go once transactions are available.

**Q5 — Does the "data is UPPERCASE" convention actually hold?** This picks the cheaper half of #15. If it genuinely holds, drop `UPPER()` from the function bodies and keep the existing bare-column indexes (free). If it does not, add expression indexes matching the predicates and drop the bare ones (a migration plus index build time). **Do not keep both spellings.**

**Q6 — Do you accept forward-only rollback plus expand-contract as policy?** Migrations run on every boot and are append-only; deploys roll back by image tag; therefore a tag rollback runs the old binary against the new schema, and MTTR for a bad release is effectively unbounded. There is no engineering fix that preserves both properties — this is a policy choice: accept forward-only (fix a bad release with a new tag) and enforce expand-contract so an image rollback is safe for exactly one version. Recommendation: accept it, document it in the README's Operations table (which has **no rollback row** today), add the post-deploy smoke check.

**Q7 — Single node forever, or eventual replicas?** The *application* is genuinely stateless and scale-ready — DB-backed sessions, advisory-locked migrations, no affinity. The *deployment* is single-node by construction. Your answer determines three things: whether httprate's in-process counters must move to a shared store (today N replicas silently means 5×N logins/min), whether the boot-blocks-listener sequence must become two-phase, and whether `PDF_RENDER_CONCURRENCY` needs to be per-node-aware. Recommendation: stay single-node and **write the constraint down** rather than pre-building for scale that may not arrive.

**Q8 — Is restating `invoice_date` after filing a real finance need?** It is currently possible on paid and cancelled invoices, with a skippable version guard and no audit trail. If finance never does this, lock it to draft and make `ifMatch` mandatory. If they do, it is a distinct audited operation with its own endpoint and history table — not a PATCH on a nullable field.

**Q9 — PDF as a queue? Verdict: no. Not a real question either.**
For one company's internal quotation/PO/invoice flow, a synchronous render behind a bounded semaphore is the correct boring choice; a job queue here is exactly the speculative abstraction to avoid. The semaphore primitive is already right — the defects are the timeouts around it (#21) and the missing container limits (#22). **The condition that flips this:** if, after #22, the semaphore's queue wait exceeds ~1s with any regularity (log it — that is the cheapest useful signal, and cheaper than Prometheus), the render has outgrown request-scope and should move to a job with a polled status endpoint. Until then, fix the failure mode, not the architecture.
